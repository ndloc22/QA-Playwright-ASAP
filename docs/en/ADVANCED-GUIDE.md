# 📚 Advanced Guide — QA Playwright Copilot Starter Kit

Detailed reference for the advanced mechanics. The root `README.md` is the short guide (3-step Quick Start); this file holds the technical detail for lookup.

> 🌐 This is the **English** version. 🇻🇳 Vietnamese original: [`../ADVANCED-GUIDE.md`](../ADVANCED-GUIDE.md).

> This starter kit is **not hard-wired to any business domain**. All examples use the generic ticket key `TICKET-123`; replace it with your real ticket key and point `BASE_URL` at your app.

## 1. Spec-Driven Testing — The Business OpenSpecs (`docs/specs/`)

Feeding all business documentation into the AI is expensive and noisy. The starter kit compresses it into a **machine-readable OpenSpec set** (YAML):

| File | Compressed content |
| --- | --- |
| `docs/specs/index.yaml` | Routing entry point + business key map (template — fill in for your project) |
| `docs/specs/process.yaml` | Process steps, statuses, REST calls, branching conditions |
| `docs/specs/roles.yaml` | Role concept, per-role visible/editable matrix |
| `docs/specs/fields.yaml` | Data-field dictionary (format, enum) + DB mapping |

> `index.yaml` ships as a **generic template**. Replace the placeholder descriptions with your real business spec (condensed from your requirement docs), and keep the `codebase_specs` block as-is (auto-generated by tooling).

**Token savings:** looking up **per ticket** (read `index.yaml` + grep exactly one spec entry) cuts >95% of the tokens compared with loading the whole source document.

### How to use it when writing a testcase
1. Identify the **ticket** or business step under test.
2. Open `docs/specs/index.yaml` to route to the right sub-spec.
3. Grep inside `docs/specs/`:
   - Step/status/REST/branch → `process.yaml`.
   - Role/visibility-edit rights → `roles.yaml`.
   - Data fields & DB mapping → `fields.yaml`.
4. Only open the original document when you need a detail the spec lacks — each spec entry should carry a `src:` field pointing to the exact source file.

### Validate YAML after editing a spec
```bash
python -c "import yaml,glob; [yaml.safe_load(open(f,encoding='utf-8')) for f in glob.glob('docs/specs/*.yaml')]"
```

## 2. Automated ticket extraction (`docs/tickets/`)

### Option 1: 1-Click Chrome Bookmarklet
1. Open the bundled bookmarklet page and drag the sync button into the Bookmark Bar (see `scripts/bookmarklet-code.txt` / `scripts/jira-sync-bookmarklet.js`).
2. While viewing any ticket in your ticketing system, click the bookmarklet.
3. Summary, Description, AC, Sprint, and Story Points are saved instantly into `docs/tickets/<KEY>.md` and `docs/tickets/<KEY>.json`.

### Option 2: Playwright Browser Automation
```bash
npm run fetch-ticket TICKET-123
# or:
npm run fetch-ticket https://your-jira/browse/TICKET-123
```
Playwright opens a browser with a persistent session (`.auth/`), extracts data via REST API, and saves it into `docs/tickets/TICKET-123.md`.

### Auto-download images/attachments + capture diagrams (Multimodal-ready)
`fetch-jira.js` also automatically:
- Scans every `<img>` and attachment link and **downloads the real binary files** into `docs/tickets/<KEY>/attachments/`.
- Separately captures each **embedded diagram** (draw.io, gliffy, canvas, iframe) into `docs/tickets/<KEY>/screenshots/diagram-N.png`.
- Captures one **full-page** screenshot as evidence (`docs/tickets/<KEY>/screenshots/full-page.png`).
- **Embeds relative image paths** directly into `docs/tickets/<KEY>.md`.

> `fetch-jira.js` targets Jira by default. For a different ticketing system, adjust the selectors/endpoints in the script.

## 3. Grounding & Reverse-Grounding in detail

### Recording the Grounding Truth (`npm run record:ticket <KEY>`)
- Reads `BASE_URL` directly from `.env` (same source as `playwright.config.ts`).
- Auto-loads the login session from `.auth/user.json` (`--load-storage`) — the tester enters the already-logged-in app. If the file is missing, the script warns and opens a logged-out browser.
- Opens `npx playwright codegen --target=playwright-test`, recording the exact selectors/flow.
- Output: `tests/recordings/<KEY>.recording.ts`.
- Jump deep into a specific screen: `npm run record:ticket TICKET-123 -- --url /path/to/screen`.

### How does `regenerate` differ from `auto-test`?
`regenerate` re-runs **exactly steps `[3/4]` + `[4/4]`** (generate Page Object/Test Spec + verify), **skipping** step `[1/4]` (fetch ticket) and `[2/4]` (summarize) because the ticket was synced earlier — faster and cheaper when you only need to regenerate after recording.

When running `regenerate` (or `auto-test`), if `tests/recordings/<KEY>.recording.ts` exists, the pipeline **automatically**:
1. Loads the recording into the prompt sent to `/new-test`, marking it as the **highest-priority Grounding Truth** — above `ui_components.yaml`/`state_machine.yaml`.
2. Generates a Page Object + Test Spec using the exact recorded selectors.
3. **Automatically removes `test.fixme(...)`** from the test cases matching the recorded flow. Flows not yet recorded keep `test.fixme(...)`.

To require a recording before generating — add the `--ground` flag:
```bash
npm run auto-test TICKET-123 -- --ground
# or:
node scripts/auto-test.js TICKET-123 --regenerate --ground
```

### Reverse-Grounding (`npm run sync-specs`)
Grounding is one-directional (OpenSpecs/recording → generate test). **Reverse-Grounding** closes the loop: it extracts the **actual** selectors/components from `tests/recordings/<KEY>.recording.ts` and **merges them back into OpenSpecs**, so the spec set **accumulates living knowledge** — future tickets immediately reuse verified selectors.

**Mechanism:**
- `scripts/sync-specs.js` analyzes the recording and extracts `getByRole`/`getByLabel`/`getByPlaceholder`/`getByText`/`getByTestId`/`getByTitle`/`getByAltText`, `page.locator('css')`, and **naming-container client ids** (e.g. `form:saveButton`), together with **actions** and **sampleValues**.
- The result is **safely merged** into `docs/specs/codebase/live_grounded_components.yaml`, each component marked `origin: live_recording_<KEY>`. Merge is keyed by KEY (idempotent).
- This file never touches `ui_components.yaml`/`state_machine.yaml`. `index.yaml` and `new-test.prompt.md` prioritize this live file above the static spec.

```bash
# Automatic: whenever auto-test/regenerate has a valid recording, the pipeline auto-syncs after step [3/4].
npm run regenerate TICKET-123

# Manual: sync one ticket, or all existing recordings
npm run sync-specs TICKET-123
npm run sync-specs -- --all
```
A recording that only navigates (no click/fill) is skipped to avoid "polluting" the OpenSpecs.

## 4. Tiered-model architecture (`npm run auto-test <KEY>`)

The pipeline runs a complete **4-step automated flow, tiered by AI model**:

| Step | Work | Model / Engine | Why |
| :-: | --- | --- | --- |
| `[1/4]` | 📥 Ingest ticket + download images/diagrams (`fetch-jira.js`) | **0 tokens** (browser scraping) | No AI needed, just DOM scraping |
| `[2/4]` | 🧾 `/summarize-story`: read ticket + images + comments + cross-check `docs/specs/codebase/` → `docs/tickets/<KEY>.summary.json` | **`claude-sonnet-5`** | Extraction/reading needs no deep reasoning — cheaper model |
| `[3/4]` | 🤖 `/analyze-story` (conflict resolution) + `/new-test` (test matrix + generate `.spec.ts`) — reads `summary.json` | **`claude-opus-4.8`** (default) | Leverage Opus's reasoning depth on the condensed summary (~30k tokens) |
| `[4/4]` | 🧪 Run `npx playwright test` to verify | **0 tokens** (local Playwright) | Executing tests needs no AI |
| *(on FAIL)* | 🩺 Self-healing: `/fix-failed-test` diagnoses + auto-fixes or exports a Bug Report, then re-runs once | **`claude-sonnet-5`** | Diagnosing technical failures needs no top-tier reasoning |

**Override the model:**
```bash
npm run auto-test TICKET-123 -- --sonnet
npm run auto-test TICKET-123 -- --model claude-sonnet-5
```
Priority order: command-line flag > env var (`AUTO_TEST_SUMMARY_MODEL`, `AUTO_TEST_ANALYSIS_MODEL`, `AUTO_TEST_SELF_HEAL_MODEL`) > default `claude-opus-4.8`.

### Step-by-step via Copilot Chat
Use this when you want to control each step and review `/analyze-story` output before generating the spec.

**Step 0 (optional): `/summarize-story`** — condense a multi-image/multi-comment ticket into `summary.json` (model `claude-sonnet-5`).

**Step 1: `/analyze-story`** — cross-check Description ⇄ AC ⇄ codebase specs ⇄ images (model `claude-opus-4.8`):
- 🔴 **Blocker** → stop, output a question table for the PO, do not generate the spec.
- 🟡 **Warning** → proceed to step 2; generated tests carry `// ⚠️ ASSUMPTION:`.

**Step 2: `/new-test`** — generate `tests/testcases/TC-<KEY>.md` + `tests/e2e/TC-<KEY>.spec.ts` (model `claude-opus-4.8`).

**Step 3: verify** — `npx playwright test tests/e2e/TC-<KEY>.spec.ts`.

**Step 4 (on FAIL): `/fix-failed-test`** — self-diagnose/fix (model `claude-sonnet-5`).

## 5. The Codebase OpenSpecs extractor (`docs/specs/codebase/`)

This spec set is extracted **directly from the real application source**, letting Copilot obtain accurate selectors/state-machines instead of guessing:

| File | Content |
| --- | --- |
| `ui_components.yaml` | Each dialog/screen: name, path, components (id, type, label, required, value binding) |
| `state_machine.yaml` | Each process: task, `responsibleRole`, transitions + branching conditions |
| `live_grounded_components.yaml` | **(Reverse-Grounding)** Real selectors/components reverse-extracted from `npm run record:ticket`. Each entry has `origin: live_recording_<KEY>`; higher priority than `ui_components.yaml`. Auto-generated, not committed. |

> 📐 For the full rationale (token economics, YAML vs JSON vs raw code, Zero-Token Preprocessing, benchmarks), see **[CODEBASE_YAML_SPECS_ARCHITECTURE.md](./CODEBASE_YAML_SPECS_ARCHITECTURE.md)**.

### Regenerate OpenSpecs (when the app codebase changes)
```bash
npm run generate-codebase-specs
# or specify a different source:
node scripts/generate-codebase-specs.js --source "D:\Projects\<your-app-source>"
```
The script scans the source **READ-ONLY** (by default targeting Axon Ivy `*.xhtml` + `*.p.json` — adjust in the script if your app uses another technology) and writes nothing back to the source project.

## 6. Blocker & Open Questions workflow (2 phases)

When `/analyze-story` detects a **Blocker**, the story **must not** produce a `.spec.ts` until the PO/BA settles the approach.

### 🚩 Phase 1 — When a Blocker is detected
1. **Stop generating `.spec.ts`** immediately.
2. **Output the standard 4-column question table** for the PO/BA:

   | Conflict location | Nature of the conflict | Decision question for the PO | Testing impact |
   | --- | --- | --- | --- |
   | (e.g. AC #3 vs `state_machine.yaml`) | (Brief description) | (Yes/No or choose A/B) | (Which tests are blocked if unresolved) |

3. **Local trace:** write the question table into `docs/tickets/<KEY>.md`, under `## 🔴 Open Questions & Blockers`.
4. **Notify the decision-maker:** post the table verbatim on the ticket and/or the chat channel. **Do not assume** on behalf of the PO.

> ⛔ The `npm run auto-test <KEY>` pipeline stops per this process (exit code 2) and prints the question table to the terminal.

### ✅ Phase 2 — After the PO/BA responds
1. **Update the Single Source of Truth first:**
   - PO edits the ticket directly → `npm run fetch-ticket <KEY>` to re-sync.
   - PO decides via comment/chat → record verbatim into `docs/tickets/<KEY>.md`.
2. **Re-run `/analyze-story`** to confirm the Clear Gate. If conflicts remain → return to Phase 1.
3. **Run `/new-test`** to generate the testcase + spec.
4. **Update the Page Object** if the story introduces a new task/dialog/component.
5. **Verify & smoke test:** `npx playwright test tests/e2e/TC-<KEY>.spec.ts`. On FAIL → `/fix-failed-test`.
6. **Commit and hand off** the ticket, testcase, spec, and related Page Object.

> 💡 **Phase 1 = Stop at the right moment** (protecting quality), **Phase 2 = Sync the source of truth before regenerating**.

## 7. Cloning the template to another project

The framework is reusable for any other web system.

1. **Clone the repo** as a starting point:
   ```bash
   git clone https://github.com/ndloc22/QA-Playwright-Copilot-Starter.git QA-Playwright-<YourApp>
   cd QA-Playwright-<YourApp>
   npm install
   ```
2. **Repoint the Codebase Specs source** to the new application source (if applicable):
   ```bash
   node scripts/generate-codebase-specs.js --source "D:\Projects\<your-app-source>"
   ```
3. **Change `BASE_URL`** in `.env` to your test server.
4. **Fill in the business OpenSpecs** from your project's requirement docs — follow the `docs/specs/` structure.
5. **Delete sample data:** `docs/tickets/*`, demo spec/tests (keep them as examples if you like).
6. Prompts (`.github/prompts/*`) **stay as-is** — that is the reusable logic.

> Separating **Prompts (reusable logic)** ⇄ **Specs/Tickets/Tests (project-specific data)** makes cloning a matter of minutes.
